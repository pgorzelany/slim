# Core 1C real programs and fast compiler loop

Date: 2026-07-22
Baseline commit: `62f44fa` (Core 1B)
Implementation parent: `8c9616a`
Host: Apple arm64, Darwin 25.3.0, macOS 26.3
Toolchain: Apple Clang 21.0.0; Rust/Cargo 1.96.0

## Outcome

Core 1C adds no SLIM syntax, type, effect, built-in, dependency, runtime ABI,
or separately parsed representation. D0030 makes performance evidence a
permanent product contract. Governance requires the executable release gates,
versioned budgets, at least twelve matched real-program challenges with the
specified coverage dimensions, and at least five matched agent repair cases.
A weaker budget requires an accepted architecture decision scoring at least
60; a stricter budget does not.

The production changes are written in SLIM. One derived declaration-name trie
is built from checked canonical tokens and discarded with the compilation
region. Calls and project atoms carry only an internal token link into the
existing declaration form. Incremental snapshots omit dependency rebuilding
when dependencies cannot be consumed, align the common snapshot fast path,
and compare qualified names without allocating a candidate for every lookup.
None of this derived state can change resolution, output, or diagnostics.

The portable compiler seed is 1,388,660 C bytes with SHA-256
`fb6921563ca0d470f14b9e096376ab707f58a2bd385fdf501a4779fdc7d99486`.
Bootstrap generations reproduce those bytes exactly. Compiler installation is
now an atomic rename, preventing an executing mapped image from being
overwritten in place during bootstrap.

## Compiler performance

Command:

```text
cargo run --release --quiet --bin slim-bench -- performance
```

| declarations | source bytes | generated bytes | check us | emit us | emit/check |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 70,862 | 540,107 | 9,013 | 15,076 | 1.673 |
| 2,000 | 143,862 | 1,082,107 | 16,305 | 28,343 | 1.738 |
| 4,000 | 289,862 | 2,166,107 | 30,809 | 54,521 | 1.770 |
| 8,000 | 581,862 | 4,334,107 | 59,293 | 106,120 | 1.790 |

Across the 8x range, process-level check and emission exponents are 0.91 and
0.94. Core 1B emitted the 2,000-declaration fixture in 251.9--254.2 ms; Core
1C takes 28.3 ms, an 8.9x improvement. Directly running the frozen Core 1B and
Core 1C compiler binaries on the same 8,000-declaration source took 4.17 s and
0.13 s. Maximum resident size fell from 33,521,664 to 32,702,464 bytes. The
name index therefore removes the superlinear work without shifting the cost
into memory.

Reduction, analysis, and proof also pass the full 8,000-declaration 1.25
scaling gates. Their measured 8,000-declaration medians are 105.8, 102.8, and
130.9 ms respectively. Raw compiler measurements are in
`2026-07-22-core-1c-compiler.tsv`.

## Incremental and project performance

At 65 modules, wide no-change/private/public sessions take 8.45/8.02/8.46 ms;
deep sessions take 8.66/8.36/8.30 ms. No-change work remains exactly
`0 0 0 0`; both edit classes remain exactly `1 1 1 1`. The six full-series
exponents range from 0.47 to 0.50, below their independent 1.25 budgets. Core
1B large private edits were roughly 39--43 ms on this host, so the current
path is about five times faster without weakened invalidation.

Serial project emission at 65 modules is 5.93 ms wide and 10.62 ms deep, with
exponents 0.42 and 0.74. Every repeated run and requested worker count emits
identical bytes. Two and four workers still show no reliable benefit on these
small graphs, so parallel execution remains opt-in and no speedup is claimed.

Raw measurements are in `2026-07-22-core-1c-incremental.tsv` and
`2026-07-22-core-1c-project.tsv`.

## Real-program corpus

The matched corpus grew from six to twelve SLIM/C11/Rust workloads. It now
covers scalar recursion, vectors, records, variants, arenas/typed IDs,
mutation, checked arithmetic, bytes/file I/O, graph work, search, sorting, and
dynamic programming. Every trio produces identical output before timing.

These are per-workload regression bounds, not a claim of general C parity.
Records, variants, byte processing, sieve, and matrix work expose clear code
quality targets. The gate keeps those costs visible and cannot justify removal
of safety checks. Complete compile/runtime/binary measurements are in
`2026-07-22-core-1c-native.tsv`.

## Agent evidence and negative results

The manifest-driven agent corpus covers unknown operations, type mismatches,
missing capabilities, non-exhaustive matches, and unterminated input. All 15
broken language/case pairs are rejected and all repairs accepted. SLIM emits
49--51 diagnostic bytes and gives 13--15 ms median process feedback here; C
emits 224--731 bytes and Rust 193--885 bytes. Source and proxy-token size vary
by case: there is still no general evidence that SLIM is smaller or that an
LLM repairs it more successfully. Raw measurements are in
`2026-07-22-core-1c-agent.tsv`.

Corpus construction exposed two diagnostics the current checker does not yet
guarantee: user-function call arity and unknown record-field access. Those
cases were not falsely counted as passing evidence. They are strong candidates
for the next compiler milestone.

## Reproduction

The full contract is:

```text
./scripts/verify.sh
cargo run --release --quiet --bin slim-bench -- performance
cargo run --release --quiet --bin slim-bench -- reduction
cargo run --release --quiet --bin slim-bench -- incremental
cargo run --release --quiet --bin slim-bench -- project
cargo run --release --quiet --bin slim-bench -- compare
cargo run --release --quiet --bin slim-bench -- agent
```

The release gate includes governance, formatting, Clippy, unit/integration
tests, all conformance and malformed-input evidence, the byte-identical
bootstrap, deterministic allocation-failure behavior, and sanitized compiler
and generated-program execution.
